The Problem

Static rules cannot keep pace with evolving fraud

Why traditional detection breaks down

  • Digital lending drives high-volume, low-latency transaction streams.
  • Fraud patterns evolve continuously — rules lag behind novel attacks.
  • Applying one model / one feature-set to every transaction is inefficient and blind to context.
  • Aggressive rules raise false positives that block genuine customers.
  • Analysts get a "fraud" flag with no reason — no basis for a fast, defensible decision.

The core challenge

“How can we dynamically analyze every transaction, identify the appropriate fraud signals, detect known and unknown patterns, and make an explainable real-time decision?”

Our answer: make the pipeline transaction-type-aware and evidence-first — the system explains what it saw, not just what it concluded.

Design principle

The platform does not blindly apply one model to every transaction. Each event is first classified, which activates only the fraud vectors that can actually occur for that product line.

Deterministic models own the risk score; the LLM only explains. The Decision Engine — not the LLM — makes the call.

Every layer exists to answer a specific question: what is this?, is it anomalous?, have we seen it before?, why?, and what do we do?

What Kafka buys us

  • Decouples transaction processing from fraud detection.
  • High-throughput, asynchronous event streaming.
  • Multiple independent consumers (scoring, audit, analytics).
  • Replay — re-run history against a new model version.

Behavioral baseline from 39-day history impl

Each account's prior 39 days are stored in PostgreSQL. On the 40th ("current") day we retrieve only that account's history (index-backed) to compute its baseline — mean/spend profile, channel mix, first/last seen — so anomalies are judged relative to the customer, not a global average.

Thresholds (implemented): risk ≥ 0.85 → decline · ≥ 0.60 → step-up · ≥ 0.40 → manual review · else approve. A consensus boost raises risk when multiple agents agree.

Guardrail: no uncontrolled financial decisions

The LLM never issues an approve/block. It returns text; the deterministic Decision Engine maps fused risk → action. This keeps the money-path auditable and reproducible.

Why this was flagged — ranked evidence

  1. Amount is significantly above the customer's historical average.
  2. Originated from a previously unseen device.
  3. Multiple transactions occurred within a short time window (velocity).
  4. Location differs from recent customer activity.
  5. Similar historical transactions were associated with fraud (vector precedent).

Efficient context retrieval — never dump the whole DB to the model

On the 40th day we fetch one account's prior-39-day rows via the composite index, compute its baseline in-service, and pass only that context to feature-engineering + embeddings. This keeps scoring fast and privacy-scoped.
