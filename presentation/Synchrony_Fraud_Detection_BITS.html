The Problem

Static rules cannot keep pace with evolving fraud

Why traditional detection breaks down

  • Digital lending drives high-volume, low-latency transaction streams.
  • Fraud patterns evolve continuously — rules lag behind novel attacks.
  • Applying one model / one feature-set to every transaction is inefficient and context-blind.
  • Aggressive rules raise false positives that block genuine customers.
  • Analysts get a "fraud" flag with no reason — no basis for a fast, defensible decision.

The core challenge

"How can we dynamically analyze every transaction, identify the appropriate fraud signals, detect known and unknown patterns, and make an explainable real-time decision?"

Our answer: make the pipeline transaction-type-aware and evidence-first — the system explains what it saw, not just what it concluded.

Why this order

Classify first, so only the fraud vectors that can occur for that product line are evaluated — the system never blindly applies one model to every transaction.

Context before scoring: PostgreSQL supplies the customer's 39-day history and Redis the hot velocity, so anomalies are judged relative to the customer.

Models decide, the LLM explains. Deterministic ML + rules + vector precedent own the risk; Bedrock only produces the reason. The Decision Engine makes the call.

A "collection of agents" (rule · ML · velocity · graph · vector) runs inside the detection service and feeds the Decision Engine.

What Kafka buys us

  • Decouples transaction processing from fraud detection.
  • High-throughput, asynchronous event streaming.
  • Multiple independent consumers (scoring, audit, analytics).
  • Replay — re-run history against a new model version.

Behavioral baseline from 39-day history impl

Each account's prior 39 days live in PostgreSQL. On the 40th day we retrieve only that account's history (index-backed) to compute its baseline — mean spend, channel mix, first/last seen — so anomalies are judged relative to the customer, not a global average.

backend/app/agents.py 
def _decision(risk):
  if risk >= 0.85: return "decline"
  if risk >= 0.60: return "step_up_authentication"
  if risk >= 0.40: return "manual_review"
  return "approve"

Guardrail: no uncontrolled financial decisions

The LLM never issues an approve/block — it returns text. The deterministic Decision Engine maps fused risk → action, keeping the money-path auditable and reproducible. A consensus boost raises risk when ≥2 agents agree.

Why this was flagged — ranked evidence

  2. Originated from a previously unseen device.
