# Demo Data — Synchrony Real-Time Fraud Detection

Synthetic dataset that feeds the fraud-detection architecture. Generated by
[`generate_demo_data.py`](generate_demo_data.py) (stdlib only, seed = 42, reproducible).

Regenerate at any time:

```bash
python3 data/generate_demo_data.py
```

| File | Contents |
|---|---|

| `accounts.json` | 165 customer accounts, with PII used for graph linking |

## What's in it

- **1,065 transactions**, **15.5% fraud** (165 fraudulent, 900 legitimate).
  > The real world is <1% fraud. We inflate it for the demo so every pipeline has
  > something to show. This is documented, not hidden.
- **All 8 product lines** represented: private_label, co_branded, promotional_financing,
  pos_installment, carecredit, digital_wallet, ecommerce, real_time_credit_application.
- **All 4 actor types**: 3P (86), B (45), S (20), M (14).
- **14 fraud vectors** with embedded, realistic patterns:

| Vector | Scenario |
|---|---|
| CB-2 | card-testing bursts (tiny auths, high decline rate, one device/BIN) |
| PF-1 | promo bust-out (clean history → max-out on resale goods) |
| X-1 | account takeover (new device + geo + contact change) |
| X-2 / APP-2 | synthetic-identity **ring** (shared device/phone/address) |
| CC-1 | CareCredit provider billing anomaly (ticket ≫ peers) |
| DW-1 | stolen-card wallet provisioning (provision → spend minutes apart) |
| EC-1 | CNP stolen card (AVS mismatch, shipping ≠ cardholder) |
| EC-5 | triangulation (one device → many addresses) |
| PL-2 | gift-card cash-out |
| CB-3 | quasi-cash cash-out (money transfer / crypto MCC) |
| CB-1 | skimming (magstripe fallback + impossible travel) |
| IL-1 | installment first-payment-default risk |
| X-5 | refund abuse (refund to a different tender) |

## Ground-truth labels

Every transaction carries a `_label` block:

```json
"_label": { "is_fraud": true, "fraud_vector": "DW-1", "actor_code": "3P", "note": "..." }
```

This is **ground truth for evaluation only** — it is **not** fed to the models at
inference time (that would defeat the purpose, and it reflects the real-world
*verification-latency* problem where the true label arrives weeks later). Use it to
score detection accuracy and to drive the demo narrative.

Fields `product_line`, `phase`, and `_label` are **demo metadata**, not part of the
real Kafka payload. The `product_line` is what the Context Resolver would *derive*;
it is included so the pipeline can be validated against the intended routing.

## How this becomes "real-time" (it's a demo)

The dataset is generated once, then split by the `phase` field:

| phase | count | role |
|---|---|---|
| `history` | 915 | **Seed** — loaded directly into Postgres so velocity counters, bust-out trajectories, and the fraud-ring graph have look-back context |
| `live` | 150 | **Stream** — replayed into Kafka on a timer during the demo |

**Flow:**

```
history (915)  ──▶  bulk-load into Postgres  (context/velocity/graph seed)
live (150)     ──▶  replay producer  ──▶  Kafka raw-transactions  ──▶  pipeline scores live
```

The **replay producer** (built in a later brick) reads `transactions.json` where
`phase == "live"`, sorted by `event_time`, and emits them to Kafka at a controlled
rate (e.g. 2–5 events/sec, with the card-testing bursts compressed into seconds).
The Fraud Detection Service consumes and scores each event as it arrives — so the
processing is genuinely real-time even though the events were pre-generated.

This mirrors exactly how fraud teams test detection systems: replay a labeled event
log through the live pipeline.

## Notes / honesty

- All data is synthetic. No real Synchrony data is used.
- Real Amazon **Store** Card = Synchrony (private label); co-brands used here are
  Sam's Club Mastercard / Verizon Visa style, consistent with the briefing's corrections.
- External signals (device reputation, bureau, SIM-swap, breach) are represented as
  fields to be filled by **mocked** enrichment services, not real vendor calls.
